How check-in works now

Students never mark themselves present. An officer records them by scanning the student's rotating QR code, and the student then confirms by signing on their own phone. That ordering is what stops a student from checking in on their own, and what gives every attendance row its own signature.

1Student registers@isufst.edu.ph email, student ID, privacy consent
2Verifies emailLink opens "choose your password"
3Shows QRSigned token, changes every 60 s
4Officer scansStaff, or an officer with a temporary grant
5Student signsPhone prompts a signature within 24 h
6ExportPDF / Excel with image, CSV with SIG- reference

What was built, phase by phase

Phase 1 — Event delegation tested live

Only users flagged canDelegate can grant access. That flag is set by a super admin, not read from the free-text "position" field, because any user can edit their own position and would otherwise be able to type "President" and promote themselves. Jared and Nikki are flagged now. A grant names one officer, one event and any of four permissions, ends at the end of the event day (or at most 24 h later if you choose a custom end), replaces any earlier grant for the same officer and event, and is checked against the database on every request, so a revoke takes effect on the next click. Nobody can grant access to themselves, and every grant, revoke and use is written to the audit log.

Staff keep the access they already had; delegation extends the same rights to other officers for one event only.

Phase 2 — Exports tested live

One report model feeds all three formats, so the columns are identical everywhere: No., Name, Position, Time In, Time Out, Method, Recorded By, Location, E-Signature. Times are in Philippine time. PDF and Excel embed the signature image; CSV can only hold text, so it carries the SIG-XXXXXXXXXX reference. Every text cell is protected against spreadsheet formula injection (a name starting with = cannot run as a formula). The PDF uses a pure-JavaScript library with no font files, so it runs on Vercel without extra setup, and it paginates large lists.

Follow-up fixes made after the first report tested live

  • Wrong site address. The code defaulted to uscattendance.syntaxure.dev, which returns 404; the live site is usc.syntaxure.dev. Password-reset and verification links would have led to a dead page. I added SITE_URL=https://usc.syntaxure.dev in Vercel Production and corrected the default in code.
  • Scanner must be at the venue. A QR scan (or a delegate's manual entry) now needs the scanner's coordinates and is refused outside the event radius, widened by the phone's reported GPS accuracy (capped at 100 m). The scanner's position is saved and shows in the export's Location column. Staff manual overrides stay exempt.
  • Student administration. Super admins get a Students page to search, correct a name, student ID or program, and deactivate or reactivate an account. Deactivation locks the student out immediately.
  • Signature retention per semester. Authorized people define each semester's dates and choose how many semesters to keep a signature (default 1) plus a grace period (default 30 days). After that, the signature image is deleted automatically each night by a Vercel cron job; the attendance record, hash and SIG- reference stay, and PDF/Excel show "image removed". Signatures outside every defined semester are never deleted, and nothing expires until the later semesters exist. There is also a "Run cleanup now" button and a count of uncovered signatures.
  • Check-in window. Each event can have an opening and closing time (none by default, so nothing changes until someone sets one). It applies to QR scans, self check-ins and delegates' manual entries; a staff manual override is exempt so an admin can always correct a record.
  • Who can change them. A super admin, the President and Secretary, or anyone with the new Settings switch in Manage Users (for the adviser and officer in charge). Every change is audit-logged.
  • Privacy page. Now describes student accounts, the officer location check and signatures.

Phase 3 — Students and signatures tested live

Registration accepts only @isufst.edu.ph addresses and answers identically whether or not the email or student ID already exists, so it cannot be used to find out who has an account. It is rate-limited per IP and per email. No password is taken at sign-up: the student sets it after clicking the emailed link. This closes a real hole I found while testing, where someone could pre-register a classmate's email with a password they knew and wait for the classmate to verify it.

The API refuses unverified students and deactivated accounts everywhere. Students cannot self check-in, read rosters, use office duty, list users, edit their own name, or be given officer access. Signatures are validated as real PNGs of sensible size, must contain actual ink, can only be submitted by the person who was checked in, once, and within 24 hours.
